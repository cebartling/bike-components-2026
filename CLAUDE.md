# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A bike components inventory app built in Swift and SwiftUI.

## Reference project

Use [investment-simulator-2026](https://github.com/cebartling/investment-simulator-2026) (same author, MIT, checked out next to this repo at `../investment-simulator-2026`) for examples and code reuse. Before writing an ADR or a component, check whether it has already solved the same problem:

- ADRs in `docs/adr/`, e.g. hexagonal architecture, Swift 6 concurrency, `@Observable` presentation models and injection, Swift Testing, CI, release
- Code such as the `HTTPTransport` test seam, the Keychain code behind its `CredentialStoring` port (here a token store inside the Strava adapter, not a Core port: ADR-0003), the `justfile` and the GitHub Actions workflows

Reuse what fits, and record where this project diverges and why. It is a macOS-only, SwiftPM-only app, so its build, bundle, window and distribution choices don't carry over to this iOS app (ADR-0002). Each ADR issue (#7 to #22) lists the relevant prior art.

## Current state

The skeleton exists (#37): `BikeComponents.xcodeproj` (app target, `@main` and composition root only), `Config/BikeComponents.xcconfig`, and the local package `BikeComponentsKit/` with `BikeComponentsCore` (ADR-0011's error enums) and `BikeComponentsUI` (`LaunchModel`, `AppModels`, `RootView`) and their test targets. No lint or format tool yet.

- `just build` builds the app for the iPhone 18 Pro simulator (iOS 27.2).
- `just test` runs every test in `BikeComponentsKit` on that simulator.
- `just test-only '<identifier>'` runs one test, suite or target, e.g. ``just test-only 'BikeComponentsCoreTests/`Source errors`/`different values or cases are not equal`(lhs:rhs:)'``. It fails when nothing matches.

## Decided

- Platforms: iPhone and iPad, one universal iOS app target. Only the latest OS release is supported, down to the point release, currently iOS/iPadOS 27.2. The minimum always equals the SDK we build with, so never write `#available` checks or fallbacks, not even for point-release APIs. When a new OS release (major or point) ships, the toolchain and minimum move up together. Not macOS, visionOS, watchOS or tvOS. Audience is the author plus TestFlight testers. UIKit only where SwiftUI has no equivalent, wrapped in the UI layer. (ADR-0002)
- Architecture: hexagonal (ports and adapters). Layering rules (ADR-0003):
  - Core (the `BikeComponentsCore` module, ADR-0004) holds the domain model, its rules (wear, service intervals, Strava import reconciliation) and the driven ports. It imports Foundation only: no SwiftUI, UIKit, Observation, SwiftData, Core Data, AuthenticationServices, Security or packages. It does no I/O (e.g. `URLSession`, `FileManager`, `UserDefaults`, `Bundle` resources) and never reads the clock or the current locale, calendar or time zone: pass them in as parameters. There is no clock port. It may create IDs with `UUID()`; any other randomness is passed in. A new import into Core needs a new ADR.
  - Core's domain model types are plain value types (use cases are `Sendable` structs or functions: ADR-0005), never `@Model`, managed objects, SQLite records or Strava JSON types. Adapters map at their boundary; Core has no DTO or mapping layer. Invariants such as unique Strava gear IDs are enforced in Core.
  - Driven ports are protocols owned by Core, named for the role (`BikeRepository`, `RideRepository`, `BikeSource`, `RideSource`). Add a port only when Core needs one. Use cases have no protocols: callers use Core's concrete types.
  - Adapters (persistence, Strava, the SwiftUI UI) depend on Core; Core depends on nothing but Foundation. Each driven adapter is its own module, created when its first code is written. Adapter-internal seams (HTTP transport, Keychain token store) stay inside the adapter; Strava tokens never enter Core. Strava connect, disconnect and connection state go through a Core port (named in #3) that the Strava adapter implements.
  - Views and presentation code use Core's types and ports only, never a driven adapter module. Only the composition root imports adapters.
  - The app target is the composition root. Core gets ports through initializers or parameters, never from singletons, globals or service locators.
  - Core is tested through in-memory fakes of its ports: no UI, disk, network or real clock. No automated import check exists yet, so check Core's imports by hand.
- Project structure (ADR-0004):
  - `BikeComponents.xcodeproj` at the repo root holds one app target, `BikeComponents`, whose sources are a buildable folder, `BikeComponents/`. It holds only `@main` and the composition root: no views, presentation code or domain logic. Code that has to sit beside `@main` (e.g. a `UIApplicationDelegateAdaptor`) is the one exception: keep it minimal and have it forward to Core or `BikeComponentsUI`. The "UI layer" for UIKit wrappers is `BikeComponentsUI`. The project file is `BikeComponents.xcodeproj/project.xcproj` (Xcode 27's JSON format, no `.pbxproj`). Make project changes (package links, groups, file references, membership exceptions, base configurations, unsetting target settings, targets and phases) with `xcrun xcodeproj`, then run `xcrun xcprojformatter --update BikeComponents.xcodeproj` (ADR-0015, below). Hand-edit `project.xcproj` only where `xcodeproj` has no command, then format it and check with `xcodebuild -list` and a build. No generator. App target build settings live in `Config/BikeComponents.xcconfig`, edited as text (ADR-0013). Capabilities (entitlements, portal) and any scheme that must be committed: ask the user to do them in Xcode. Never hand-edit an `.xcscheme`. App resources (asset catalog, `Info.plist`, entitlements) live in `BikeComponents/`.
  - Every module lives in the local package `BikeComponentsKit/` (`Sources/<Module>/`, `Tests/<Module>Tests/`), iOS only. Its one library product, `BikeComponentsKit`, lists every library target and is the only thing the app links. Add a new module to that product's targets. Modules: `BikeComponentsCore` (Foundation only), `BikeComponentsUI` (views and presentation code; depends on Core only), `BikeComponentsPersistence` and `BikeComponentsStrava` (driven adapters; depend on Core). Only the app target depends on adapter modules. Every module name starts with `BikeComponents`. Adding or splitting a module that fits these rules needs no ADR. A new kind of module, or one that breaks these dependencies, needs a new ADR. Package targets' Swift settings go in `Package.swift`. Create a module with its first code, and give each library module a `<Module>Tests` test target. `BikeComponentsTestSupport` (shared fakes) is the exception: not in the product and no test target (ADR-0012, below). `BikeComponentsUITests` is the unit test target of `BikeComponentsUI`. Xcode suggests the same name for a UI test target of the app, so an Xcode UI test target must not use Xcode's default name.
  - Access control: `package` for what another package module uses, `public` only for what the app target uses, `internal` (or narrower) otherwise.
  - Third-party packages follow ADR-0006 (below): only the module that needs one (and its tests) uses it, never Core or the app target.
  - Tests run on an iOS Simulator with `xcodebuild` against the package's generated `BikeComponentsKit` scheme, from `BikeComponentsKit/`, which picks up every `.testTarget` by itself (the three-step recipe: ADR-0012, below). Xcode's automatic `BikeComponents` scheme only builds and runs the app; no scheme file is committed (ADR-0015). `swift build` and `swift test` on the Mac are not supported: they may build and pass, but they test macOS, which isn't a supported platform, so don't rely on them.
- Concurrency (ADR-0005):
  - Swift 6 language mode in every target. Every target enables the upcoming features `NonisolatedNonsendingByDefault`, `InferIsolatedConformances` and `MemberImportVisibility`: package targets through one shared settings list in `Package.swift`, the app target through its `SWIFT_UPCOMING_FEATURE_*` settings in `Config/BikeComponents.xcconfig` (ADR-0013), with the template's `SWIFT_APPROACHABLE_CONCURRENCY` set nowhere. `Package.swift` needs `swift-tools-version` 6.2 or later. Don't enable other upcoming features without a new ADR.
  - Default isolation: Core, Persistence and Strava are nonisolated. `BikeComponentsUI` (`.defaultIsolation(MainActor.self)`) and the app target are `MainActor`. A test target uses its module's isolation. In a main-actor module, mark a type `nonisolated` when it has to leave the main actor.
  - A nonisolated `async` function runs on its caller's actor; actor and main-actor methods run on their own. Use `@concurrent` (only on `async` functions) to move work off the caller deliberately.
  - Core has no actors and no shared mutable state. Domain types are value types that declare `Sendable`. Use cases are structs that declare `Sendable` (it isn't inferred for `public` types), or functions, holding their ports, `async` when they call a port.
  - Driven ports are `Sendable` protocols, `async` for I/O. Adapters hide their isolation behind the port and never block their caller: put blocking or CPU-heavy work in a `@concurrent` function or on the adapter's own actor. Use an actor for adapter state that concurrent calls share, such as the Strava token store and refresh. Actors are reentrant, so the token actor keeps a refresh in progress as a stored task that concurrent callers await, so only one refresh runs at a time. A `Sendable` port can't have an isolated conformance, so a main-actor type implements a port only through `async` methods. The persistence adapter's isolation is set by ADR-0007 (below).
  - In-memory fakes of ports are actors, or final classes that guard their state with Synchronization's `Mutex`. Test targets may import Synchronization (Core's Foundation-only rule covers `BikeComponentsCore`, not its tests).
  - Prefer an actor or a value type. A synchronous adapter class may guard its state with Synchronization's `Mutex`. `@unchecked Sendable`, `nonisolated(unsafe)` and `@preconcurrency` only with a comment saying why the code is safe or which framework forces it.
  - Use structured concurrency (`async let`, task groups). Start unstructured tasks in the UI layer, preferably with `.task`. An adapter may start one only for a task in progress that several callers share or for an `AsyncStream` producer: keep the handle, cancel it when it's no longer needed, and comment why. No `Task.detached`, Dispatch, completion-handler APIs or Combine. Wrap callback-only framework APIs in checked continuations inside the adapter. Use `AsyncSequence`/`AsyncStream` for values over time, and stop the producer when the consumer is cancelled.
  - Long-running work (a Strava import) checks for cancellation between pages, stops promptly, keeps what it already saved, and isn't reported to the user as an error when cancelled. Cancellation is reported as a `cancelled` case of the typed error (ADR-0011). Back-off waits use a cancellable sleep, injected (ADR-0011).
  - No global mutable state: globals and `static`s are `let`s of `Sendable` types.
- Dependencies (ADR-0006):
  - Apple's frameworks first. Never add a package (a `.package` entry, a test-only package, a macro or plugin package, a binary target, or one of Apple's open-source packages outside the SDK) or a tool without an accepted ADR that admits it. You may propose one in an ADR pull request; the user approves by merging.
  - A package's admitting ADR has a "Dependency check" section and must show it clears the bar: MIT, BSD, Apache-2.0, ISC or zlib license (no GPL, LGPL or AGPL), the same for every transitive dependency, built from source (no binary targets), maintained (a release or commit within 12 months, builds with the current Xcode for iOS), usable in Swift 6 mode without concurrency escapes in our code, no data collection unless that is its job, and imported by exactly one named module and its test target (a test-only package: only the test targets its ADR names), never Core, Core's test target or the app target. Its types stay inside that module. Another license, a binary target or a concurrency escape is allowed only if the admitting ADR argues for it. Macros and build plugins also count their build cost against them. See ADR-0006 for the full bar and the fields the dependency check records.
  - Pin each package with `exact:` in `Package.swift`, with a comment `// ADR-NNNN: used only by <Module>.` No ranges, branches or revisions. Commit `BikeComponentsKit/Package.resolved` and the Xcode project's resolved file, and update both when a pin moves. A resolved-file change that moves a transitive dependency is checked against the bar too. CI builds with `-onlyUsePackageVersionsFromResolvedFile`.
  - Updates are manual, one package per pull request, checked when the toolchain moves to a new Xcode or a security fix ships (Dependabot security alerts, not version-update pull requests, are on once the first package arrives). The pull request description repeats the dependency check; don't edit the admitting ADR. An update that no longer clears the bar needs a new ADR. If a package has no version that builds with the new Xcode, or no longer clears the bar, stop the toolchain move and ask the user: a new ADR replaces it, removes it or accepts the exception.
  - Tools are standalone binaries (Homebrew locally), never SwiftPM plugins or packages, even where a plugin version of the tool exists. Formatters and linters are pinned in CI by version and SHA-256; `just` may be unpinned. CI prints every tool's version. When you upgrade a tool locally, move its CI pin in the same change. Actions from GitHub's `actions` org are pinned by major tag; any other action by full commit SHA with its version in a comment.
- Persistence (ADR-0007):
  - One app-wide SwiftData store, `BikeComponents.store` in Application Support. Only `BikeComponentsPersistence` imports SwiftData: not Core, `BikeComponentsUI` or the app target. Its public API opens the store and returns the adapter, through an `async` `@concurrent` function so opening and migrating never run on the main actor. The app's store syncs through CloudKit (ADR-0009, below); test stores pass `cloudKitDatabase: .none`.
  - Fail fast: if the store can't be opened or migrated, throw an error naming the path and the cause, and the app shows it. Never delete, recreate or replace the store with an empty or in-memory one.
  - `@Model` classes are internal to the adapter. Port methods take and return Core value types. Records keep the domain `UUID` as an attribute, and the adapter finds them by it. Mapping a record that can't make a valid Core value throws a descriptive error.
  - The schema follows CloudKit's rules: every attribute optional or defaulted, every relationship optional with an explicit inverse, no `@Attribute(.unique)` or `#Unique`, no `.deny` delete rules. Core enforces uniqueness. Writes upsert by the domain `UUID` (fetch, then update or insert). Saving a bike also fetches by gear ID in the same actor call and throws if a bike with another `UUID` holds it. Only one import runs at a time (how is decided with #3).
  - Threading: one plain actor (not `@ModelActor`, which ran on the main thread when called from the main actor) creates a `ModelContext` from the container in its initializer, keeps both, and implements every repository port. Set `autosaveEnabled` to false explicitly, leave `undoManager` nil, and every write method calls `save()` once before it returns.
  - Migrations: a `VersionedSchema` from `SchemaV1` and a `SchemaMigrationPlan` from the start. Stages are lightweight unless data must be transformed. A version that has reached a TestFlight build is frozen. Each stage has a test that writes an old-version store to a temporary file and reopens it. All other adapter tests use an in-memory configuration, one container per test.
  - The thread checks ran on macOS. The adapter's first tests must check on the iOS Simulator that a port method called from the main actor runs off the main thread, with Core Data's concurrency assertions on (`com.apple.CoreData.ConcurrencyDebug` = 1, passed through the `.xctestrun` file: ADR-0012, below). If either check fails, stop and revisit ADR-0007.
- State management (ADR-0008). Every feature follows this pattern:
  - Domain rules live in Core. Screen logic lives in an `@Observable` presentation model in `BikeComponentsUI`: screen state, intent methods (`load()`, `save()`, …) that call Core's use cases and ports, and mapping of results and errors to display state (errors: ADR-0011). Derived values are computed properties.
  - A model is an `@Observable final class` named `<Screen>Model`, main-actor through the module default, never `nonisolated`, and declares no `Sendable` conformance (main-actor isolation makes it implicitly `Sendable`). No `ObservableObject`, `@Published`, `@StateObject`, `@ObservedObject` or `@EnvironmentObject`.
  - Each model is in its own file, `<Screen>Model.swift`, in `Sources/BikeComponentsUI/Presentation/` (grouped by feature inside it). Every file there (models, their extensions, the display-state types they expose) imports Foundation, Observation and `BikeComponentsCore` only, never SwiftUI or UIKit. Views live outside that folder. The compiler only stops a model naming SwiftUI's declarations: review checks that models don't reach view-side declarations (typealiases, inferred SwiftUI types, views).
  - A model's initializer stores its dependencies and sets initial state only: no port calls, no tasks. Loading is an `async` method the view calls from `.task`.
  - Intent methods that call Core are `async`. Views call them from `.task`, `.task(id:)`, `.refreshable` or a `Task` in a button action. A model starts no unstructured task, except an app-wide model running work that must outlive a screen (the Strava import), which keeps the handle, can cancel it and comments why. A button `Task` isn't cancelled with the view, so intents report their outcome in state or a return value and the view only acts on it (`if await model.save() { dismiss() }`).
  - Views are thin: they read model state, bind with `@Bindable`, call intent methods, and never call a use case or port. View `@State` holds only ephemeral state no rule depends on (focus, scroll position, confirmation dialog shown, section expanded). Selection, navigation state and which sheet or destination is presented are model state (ADR-0014, below). A view with only ephemeral state needs no model. A model may own the models of the parts it presents.
  - Models expose values, not formatted text. Views format with `FormatStyle` through `Text(_:format:)` and similar APIs, which apply the environment's locale; a view calling `formatted(_:)` itself passes the environment's locale. A model that needs the current date, a calendar or a time zone gets it passed in (how: ADR-0010, below). APIs only a view can reach (e.g. the `webAuthenticationSession` environment value) are called by the view, which hands the result to the model (what is handed over: #3).
  - The store is the source of truth. Models hold copies loaded through Core, load when their screen appears and reload (or update from the use case's result) after their own writes. When a write changes another screen on display, the model that owns both refreshes the other (a view that owns both only chains the two intent calls). No app-wide cache of domain data, and no change-notification port yet (revisit if refreshing by hand gets awkward). Writes from other devices come through ADR-0009's remote-change port (below).
  - App-wide state (Strava connection state, import progress) lives in app-wide models built once by the composition root and kept in `@State` on the `App`. Ones that need a repository are built after the store opens (ADR-0007: async, can fail); until then the `App` holds the launch model (ADR-0010, below), which keeps them once they are built. The import runs there, so it outlives the screen that started it and can be cancelled. Cancellation isn't shown as an error. A screen showing imported data is given the import model and reloads when it reports saved progress (e.g. `.task(id:)` on a counter it exposes; what it reports: #3).
  - Every model has one owner: the `App`, or the view (`@State`) or model that presents the screen. A view given a model holds it as `let` or `@Bindable var`, never `@State`. A view that keeps a model built from an input (e.g. a bike ID) in `@State` gets `.id(input)` so the model is rebuilt when the input changes, or its parent model owns the model and passes it in. Models reach views through view initializers, never `@Environment`. Owners build models through factory closures, and nothing besides the system frameworks' own values goes in the environment (ADR-0010, below).
  - Model tests in `BikeComponentsUITests` build models with Core's real use cases over in-memory fakes of the ports, call intent methods and check state. Views have no unit tests.
- Sync and backup (ADR-0009):
  - SwiftData's CloudKit mirroring syncs the whole store (bikes, rides, components, installations, service records) to the user's private CloudKit database. The app's `ModelConfiguration` passes `cloudKitDatabase: .private(<container identifier>)`, never `.automatic`. Adapter tests keep `.none`. No export or import file yet. Per-device state (an import's resume point, last sync time) never goes in the synced store; where it lives is decided with #3.
  - The iCloud (CloudKit, with the container) and Background Modes (Remote notifications) capabilities are Xcode project changes: ask the user. Only `BikeComponentsPersistence` knows about CloudKit; it may import Core Data for the debug-only schema initialization.
  - The store works without iCloud: a signed-out user is not an error. Forum reports (unverified) say signing out later removes the local copy and can lose changes not yet uploaded. ADR-0007's fail-fast rule still applies when the store can't be opened or migrated.
  - Duplicates from other devices are expected. Core reconciles bikes sharing a Strava gear ID and rides sharing a Strava activity ID: keep the smallest `UUID`, move everything app-owned (installed components, installations, service records and any other app-owned data) to it, delete the rest, all in one port call and one save. Reconcile bikes before rides; rides on a losing bike move to the winner, and a ride whose bike is missing is linked by its stored Strava gear ID. A bike save that fails ADR-0007's gear ID check because a duplicate arrived is expected: Core reconciles and retries once; a second failure is a real error. Reconcile at launch, when the app becomes active, at the start of every import (before its upserts), and when the remote-change port reports changes from another device. Scan the whole store; no history token. Reconciliation runs under the imports' one-at-a-time guard: never during an import's page, and the import reloads its bikes after one. Combine triggers that arrive while one is running or waiting.
  - Remote changes: one narrow Core port (an `AsyncSequence`, implemented by the persistence adapter) reports only that changes from another device arrived, not which records. An app-wide model on the `App` consumes it from the root view's `.task`, runs reconciliation for each report, then increments a counter; screens showing synced data take that model and reload with `.task(id:)` on it. Repositories still don't publish changes (ADR-0008), and this device's own writes refresh screens as ADR-0008 says.
  - Conflicts are the framework's (reported as last writer wins; Apple doesn't document it); add no conflict handling. Deletes propagate to every device and are permanent.
  - Once a schema version is deployed to CloudKit production, later versions only add models and attributes: never delete, rename or change the type of existing ones. Devices may run different app versions, so a new attribute's default must map to a valid Core value. Records can arrive before their parents: reads skip a record whose required relationship hasn't arrived (it's incomplete, not invalid; any other unmappable record still throws), and reconciliation never matches on a missing Strava ID. Initialize the development schema by hand from a debug build when the schema changes (a debug-only public function in `BikeComponentsPersistence`, called by the app only when a launch argument asks); deploy to production in the CloudKit Console before a TestFlight build with a new schema version.
  - Strava tokens never sync: each device that imports connects to Strava itself, with non-synchronizable Keychain items.
  - The cross-context checks ran on macOS without CloudKit. Before the first TestFlight build with sync, check on two devices that imported changes are seen and reconciled, that a signed-out device works, what signing out and back in does to changes not yet uploaded, and that the store opens when iCloud is unavailable or full. If not, stop and revisit ADR-0009.
- Dependency injection (ADR-0010):
  - Initializer injection everywhere: Core, adapters, models, views. No property injection, container, service locator, DI library or dependency in the environment. No default arguments for dependencies (ports, factories, clock, calendar, system shared instances an adapter takes): every caller, tests included, passes them.
  - Models take the Core ports they use (`any BikeRepository`, …) and build the use cases they call from them. Views get a model, or a factory closure for the model they keep in `@State`, never a port, adapter or use case.
  - Child models come from factory closures that take only what varies (`makeDetailModel: (UUID) -> BikeDetailModel`), written by the composition root. Use a factory even when the parent could build the child itself. A parent's test passes a closure building the child over the same fakes.
  - The composition root is the `@main` `App` plus plain file-level wiring functions in `BikeComponents/`, one per model, taking the opened ports as parameters and returning the model or its factory closure. Only it names adapter types, opens the store, builds the Strava adapter, and passes `{ Date.now }` and `Calendar.autoupdatingCurrent`. Everything the wiring names is `public` (ADR-0004): model initializers, `LaunchModel`, `AppModels` with an explicit `public init`, the root view, adapters' open functions and initializers, and the ports and Core types in those signatures. Use cases stay `package`. Each adapter is built once. It holds no logic and has no unit tests: anything with a decision goes in a model. Exceptions: ADR-0009's launch-argument check for schema initialization, and ADR-0004's delegate adaptor beside `@main`.
  - Launch: `App.init` opens nothing and keeps only `LaunchModel` (in `BikeComponentsUI`) in `@State`. It takes `start: () async throws -> AppModels` from the composition root, which opens the store, builds the adapters and returns `AppModels` (the app-wide models and a factory for the root screen's model, which the view showing the app builds and owns; one scene: ADR-0014, below). State: opening, ready(`AppModels`) or failed(error). The root view calls `launch()` from `.task`. The first call starts `start` in a task the model stores (ADR-0008's app-wide exception, with a comment) and every call awaits that task, so the store opens once and a view going away never cancels the launch. Every app-wide model is built by `start`, and kept on the `App` through the ready state. The view shown in the ready state is ADR-0009's root view: its `.task` runs the remote-change model. A failed launch shows the error until relaunch: no retry, no fallback store. Wording: ADR-0011.
  - The current date is `now: () -> Date`, called each time an intent needs it, never from a computed property (keep date-derived values in state); a calendar or time zone is a `Calendar` (use its `timeZone`). Tests and previews pass fixed values. Core and `Presentation/` files never use `Date.now`, `Date()`, or `.current`/`.autoupdatingCurrent` of `Calendar`, `TimeZone` or `Locale`.
  - Fakes go in through the shipping initializers: no test-only or preview-only initializers, no "am I in a test or preview" checks in shipping code. One in-memory fake per port, written when a test first needs it and shared by the test targets that need it (in `BikeComponentsTestSupport`: ADR-0012, below). Previews, if #19 adopts them, use the same fakes and fixed date and calendar, never the real store, Strava or Keychain.
  - No singletons of our own anywhere (`static let shared`, globals or statics holding a dependency, type-based resolvers). `Sendable` `let` constants are fine. System shared instances (`URLSession.shared`, `FileManager.default`, `UserDefaults.standard`, `NotificationCenter.default`, `UIApplication.shared`) only in the driven adapters (persistence, Strava) and the composition root; an adapter takes one through its initializer when its tests need to replace it. Views use environment actions (`openURL`) instead. A UIKit wrapper in `BikeComponentsUI` that needs one is given it through its initializer, passed from the composition root.
  - No custom `EnvironmentValues` entries yet. One for a view-only concern no model reads needs no ADR; one carrying a dependency does.
- Networking and errors (ADR-0011):
  - No networking package. `BikeComponentsStrava` declares a public `Sendable` `HTTPTransport` with one method, `send(_ request: URLRequest) async throws -> (Data, HTTPURLResponse)`, implemented by `URLSessionTransport`, which takes its `URLSession` with no default. The composition root passes an `.ephemeral` session with `timeoutIntervalForRequest` = 30 s. An internal client builds requests, adds the bearer token, reads rate-limit headers, maps statuses, decodes and retries, in a `@concurrent` request function. Port implementations never touch `URLRequest` or the transport. The transport throws `URLError(.badServerResponse)` for a non-HTTP response. `URLError(.cancelled)` while the task isn't cancelled is `unavailable`, never retried.
  - Token refresh lives in the token actor: refresh when the token expires within an hour (Strava's threshold). A `401` on a request sent with a token forces one refresh and one retry: the client hands the actor the failed token, and the actor refreshes only if it still holds that token, else it returns the newer one (concurrent `401`s cause one refresh; test it); a second `401`, or the token endpoint answering a refresh with a `4xx` other than `429`, is `authorizationRejected`. No stored tokens is `notConnected`. The token actor produces both, and the client passes them on. A caller's cancellation never cancels the refresh task, so a rotated refresh token is always saved.
  - Typed throws on every port method, use case and Core rule that can fail, with error enums owned by Core, `Equatable`. Never write `default:` in a switch over our error enums. One enum per port family: `SourceError` for the Strava ports (`notConnected`, `authorizationRejected`, `rateLimited(resetsAt:)`, `offline`, `unavailable(detail:)`, `unreadableResponse(detail:)`, `cancelled`), `RepositoryError` for repositories (`gearIDTaken(heldBy:)`, `unreadableRecord(detail:)`, `storeFailed(detail:)`). A use case calling several port families throws its own enum wrapping them (`.source(SourceError)`, `.repository(RepositoryError)`) plus its own failures, and doesn't re-spell port cases. `RepositoryError` has no `cancelled` (store calls don't stop for it); the import's enum has its own `cancelled` for its between-pages check. Adding a case needs no ADR.
  - Adapters catch every framework error (`URLSession`, `JSONDecoder`, SwiftData, Keychain, `Task.sleep`) and map it before the port method returns. Check `Task.isCancelled` first: anything thrown while cancelled is `cancelled` (`URLSession` throws `URLError(.cancelled)`, not `CancellationError`). Then, in order: no stored tokens → `notConnected`; `URLError` `.notConnectedToInternet`, `.dataNotAllowed`, `.internationalRoamingOff` → `offline`; the token endpoint answering a refresh with a `4xx` other than `429`, or a `401` after refresh and retry → `authorizationRejected`; `429` → `rateLimited`; other `URLError`s, `5xx` after retries and other statuses → `unavailable`; decode or mapping failures → `unreadableResponse`. `detail` is built from chosen parts: method and path (never the query), HTTP status, a `URLError`'s code by name and number, a store error's type and `localizedDescription`, or the type and coding path that didn't decode. Never `String(describing:)` of an `NSError`/`URLError` (it prints the full URL with its query), headers, bodies, tokens, the client secret or an authorization code. Never put tokens, the client secret or authorization codes in a URL.
  - Cancellation is the `cancelled` case, not `CancellationError`. Models treat every `cancelled`, wrapped or not, as no error and restore the screen's state from before the intent, except what the work already saved (a cancelled import keeps its progress; screens reload as ADR-0008 says).
  - Models switch over every case and map it to display state holding the Core error (or a screen enum), never text. Views word errors: one wording function per Core error enum in `BikeComponentsUI`, outside `Presentation/`. No `localizedDescription` or `LocalizedError` for wording. A failed load replaces the content with the error and a retry; a failed action shows an alert. Show a case's detail as secondary text. The persistence opening function throws its own `public`, `CustomStringConvertible` error type (typed throws), naming the path and cause; `start` stays untyped (ADR-0010's signature). A failed launch shows a fixed sentence plus `String(describing: error)`. No iCloud sync status yet.
  - DTOs are internal `Decodable` structs in the adapter with explicit `CodingKeys` (no `.convertFromSnakeCase`: it maps `gear_id` to `gearId`, so `gearID` silently decodes as `nil`). Optional only where Strava omits or nulls a field. Open-ended values such as `sport_type` decode as `String`. Dates use `.iso8601`; never decode `start_date_local` as a `Date` (its `Z` is wrong).
  - Only the Strava client retries requests (ADR-0009's reconcile-and-retry of a bike save that throws `gearIDTaken` is unchanged): `GET`s after a transient `URLError` (not offline or cancelled) or `500`/`502`/`503`/`504`, at most twice, after 1 s and 2 s. Never retry `POST`s, `429`, other `4xx`, offline, decode failures or cancellation. A failed refresh leaves the stored tokens as they were, so the next request tries again. A `429` throws `rateLimited(resetsAt:)` (next midnight UTC if a daily usage has reached its limit, else the next quarter hour); the adapter never waits it out. Whether an import waits is #3's. Check cancellation before each attempt.
  - The Strava client and token actor take `now: @Sendable () -> Date`, and the client takes `sleep: @Sendable (Duration) async throws -> Void` (so does the import model if #3 has it wait), with no defaults; the composition root passes `{ Date.now }` and `{ try await Task.sleep(for: $0) }`. Tests pass a fixed date and a recording sleep that returns at once or throws `CancellationError`.
  - `Task` closures never declare typed throws (a `Task` can only be created with failure `any Error` or `Never`, and a typed-throws `Task` closure crashes Swift 6.4.2 when the error carries a value). Use a non-throwing closure that catches inside and keeps the outcome in state or returns a `Result`.
  - `async let` and `withThrowingTaskGroup` also erase typed errors to `any Error`. Parallel typed-throwing work uses `async let` of a non-throwing closure returning `Result`, or `withTaskGroup(of: Result<T, SomeError>.self)`, unwrapping with `try result.get()` after the group returns. Values over time that can fail: `any AsyncSequence<Element, SomeError> & Sendable` or `AsyncStream<Result<Element, SomeError>>`, never `AsyncThrowingStream` (it can't take a typed failure). A sequence that can't fail (ADR-0009's remote-change port) has failure `Never`.
  - Strava adapter tests use a fake `HTTPTransport` (final class with `Mutex`) answering by method, path and query and recording requests, plus scrubbed real-response fixture JSON in `Tests/BikeComponentsStravaTests/Fixtures/`, read through `Bundle.module`. Each fixture test asserts the optional fields it contains are read (a misspelled key decodes as `nil`). `URLSessionTransport` has no unit test.
- Testing (ADR-0012):
  - Swift Testing only (`@Test`, `@Suite`, `#expect`, `#require`, `confirmation`, `@Test(arguments:)`). No XCTest; it is only for what Swift Testing can't do (UI tests, `measure`), and neither is adopted.
  - Core is the main test target: anything with a rule goes in Core. Models are tested in `BikeComponentsUITests` (real use cases, fake ports, fixed `now` and `Calendar`), persistence against in-memory stores, Strava through ADR-0011's fake transport and fixtures. Views, the composition root, `URLSessionTransport` and CloudKit have no unit tests.
  - No XCUITest target and no snapshot tests or snapshot package. Revisit UI tests with #19 or when a navigation bug gets past the model tests (ADR-0014; named other than `BikeComponentsUITests`), snapshots with #19.
  - Fakes, not mocks: working in-memory implementations named `Fake<Port>`, which may record calls and be told to throw a given error from a given method. No mocking library, no fakes of use cases. A fake that models an adapter rule (such as `gearIDTaken`) is checked by the same test in the adapter's test target, parameterized over which implementation to build (an enum such as `fake`/`real`, never live instances); the test body builds a new instance, so the adapter's test target depends on `BikeComponentsTestSupport`.
  - Shared fakes of Core's ports, and helpers that build Core values for several test targets, live in `BikeComponentsTestSupport` (`Sources/BikeComponentsTestSupport/`): a `.target` depending on Core only (Synchronization allowed; no adapters, UI, SwiftData or `Testing`), nonisolated, `package` declarations, not in the `BikeComponentsKit` product, depended on only by test targets, with no test target of its own. Adapter-internal fakes (`HTTPTransport`, Keychain) and fixtures stay in the adapter's test target.
  - No previews yet: #19 decides, including where their fakes live (not via `BikeComponentsUI` depending on `BikeComponentsTestSupport`, which would ship the fakes).
  - Suites are structs and tests are sentences, both raw identifiers (``struct `Service intervals` ``, ``@Test func `a chain is due after 3000 km`()``), in `<Subject>Tests.swift`. Every test is in a suite, and names contain no `/`. Parameterize tables. `#require` for preconditions. Each test builds its own state (suite `init` or the test body); no mutable state shared between tests (`static`s and globals are `Sendable` `let` constants only); tests run in parallel, `.serialized` only with a comment. `@testable import` only where a test needs `internal` declarations.
  - Async: tests are `async` and await what they test; never sleep or poll. Pass fixed `now`, `Calendar` and a recording `sleep`. Test `AsyncSequence`s inside `confirmation(expectedCount:)`, finishing the sequence from the fake. Test cancellation by cancelling a task at a point the fake controls: the fake cancels its caller with `withUnsafeCurrentTask { $0?.cancel() }` on a chosen call (a really cancelled task, needed for the import's between-pages check), or the recording sleep throws `CancellationError`. Test isolation follows the module; `@MainActor` on a test that checks where a port runs.
  - Persistence tests: one in-memory adapter per test (`cloudKitDatabase: .none`) from a helper that returns the adapter, which keeps the container and context; never return a context without its container. Migration tests use a new `UUID`-named directory under `FileManager.default.temporaryDirectory` and remove it, recording a failed removal as a test issue.
  - Running tests (the `justfile` arrives with the skeleton; `just` is admitted by ADR-0012, CC0-1.0 as an argued exception to ADR-0006's OSI rule, installed with Homebrew, unpinned in CI): `just test` runs everything, `just test-only '<identifier>'` runs one test, suite or target. The recipe runs `xcodebuild build-for-testing`, adds `-com.apple.CoreData.ConcurrencyDebug 1` to every test target's `CommandLineArguments` in the `.xctestrun` file, runs `xcodebuild test-without-building -xctestrun` with a result bundle, and fails when `xcrun xcresulttool get test-results summary` reports `totalTestCount` 0 (a filter that matches nothing otherwise passes). The identifier reaches `xcodebuild` positionally (`set positional-arguments`, `"-only-testing:$1"`), never through `{{identifier}}`, which hands the backticks to the shell. Use the `.xctestrun` this build wrote, and remove the old result bundle first. Identifiers are `<TestTarget>/<Suite>/<test>()` with raw identifiers' backticks kept, plus argument labels for parameterized tests: ``just test-only 'BikeComponentsCoreTests/`Service intervals`/`a chain is due after 3000 km`()'``.
- Build configuration and secrets (ADR-0013):
  - Every app target build setting lives in `Config/BikeComponents.xcconfig` (repo root, outside the buildable folder), the target's base configuration for Debug and Release. That includes `IPHONEOS_DEPLOYMENT_TARGET` (deleted at the project level, where the template puts it), ADR-0005's Swift settings (with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`), versions, signing (`CODE_SIGN_STYLE`, `DEVELOPMENT_TEAM`: committed, since it isn't secret and the project has one author; another developer overrides it in `Config/Secrets.xcconfig`) and generated `Info.plist` keys. The target level of the project holds no build settings (`xcrun xcodeproj setting list --target BikeComponents` reports none): a target-level value beats the file. Project-level settings stay as Xcode's template wrote them. Only Debug and Release; add a per-configuration file only when a target setting first differs between them.
  - Change settings by editing the file as text, never in Xcode's Build Settings editor (it writes at the target level). When Xcode writes a target-level setting anyway (e.g. `CODE_SIGN_ENTITLEMENTS` from a capability), move it into the file in the same change and remove it with `xcrun xcodeproj setting unset <key> --target BikeComponents`. Review checks the target has no build settings.
  - In an `.xcconfig`, `//` starts a comment: write URLs as `https:/$()/host`.
  - Per-developer or unpublishable values go in `Config/Secrets.xcconfig`, git-ignored (add it to `.gitignore` before the file exists; the repo is public). `Config/BikeComponents.xcconfig` declares each such setting empty and ends with `#include? "Secrets.xcconfig"` as its last line. A missing file builds silently with empty values.
  - Values reach code through `BikeComponents/Info.plist` keys set to the build setting (`$(STRAVA_CLIENT_ID)`), merged with the generated plist (the file exists and is excluded from the buildable folder: ADR-0015). Only the composition root reads them, with `Bundle.main.object(forInfoDictionaryKey:)`, passing the string (empty if missing) to the adapter's initializer. The adapter's public initializer or configuration type throws a typed error naming the empty field (not the key, which it doesn't know; the launch wording or README maps the field to its setting), so the launch fails with it. #3 names the Strava settings and decides whether the client secret is embedded; anything in `Info.plist` is readable from the `.ipa`.
  - CI builds and tests without the secrets file. Secrets are never committed, logged or put in URLs (ADR-0011). `-showBuildSettings` and run-script environments expose every build setting: a job holding the secrets file never prints build settings, and no script phase echoes its environment.
- Navigation and scenes (ADR-0014):
  - One `WindowGroup` scene and one window: `UIApplicationSupportsMultipleScenes` is `false` in the `UIApplicationSceneManifest` dictionary of `BikeComponents/Info.plist` (no `INFOPLIST_KEY_*` setting exists for it, so not in the `.xcconfig`). A generated scene manifest overrides it with `true`, so `INFOPLIST_KEY_UIApplicationSceneManifest_Generation = NO` and `Info.plist` holds the whole manifest, with an empty `UISceneConfigurations` (ADR-0015). Check the built app's `Info.plist` with `plutil -p` after changing either. No `DocumentGroup` or other scene types. The ready-state view builds one root screen model from `AppModels`' factory; navigation state lives there, not in an app-wide model.
  - The root screen is a two-column `NavigationSplitView` (sidebar: bikes and other top-level entries such as unassigned rides; detail: the selected entry), one layout for every width, collapsing into one stack on iPhone and in narrow iPad windows on its own. No `TabView` root, no three-column split.
  - The root screen's model holds `selection`, an optional `Hashable` enum in `Presentation/` (`.bike(UUID)`, `.unassignedRides`, …) bound to `List(selection:)`, and `path`, an array of a `Hashable` enum in `Presentation/` (`.component(UUID)`, `.ride(UUID)`, …) bound to the detail column's `NavigationStack(path:)`, with one `navigationDestination(for:)` at the stack's root. Routes carry domain `UUID`s, never domain values. The model never selects on its own: with nothing selected, a regular width shows a placeholder detail (design: #19). Views push with `NavigationLink(value:)`; only the root screen's model's own intents change `path`. A pushed screen leaves with `dismiss()` on its intent's outcome (`if await model.delete() { dismiss() }`). No `NavigationPath`, `NavigationLink(destination:)`, router or coordinator.
  - Changing the selection clears the path. The root screen's model holds the detail as an optional enum (one case per kind of entry, holding its model) and rebuilds it from a factory whenever the selection changes, with no port call; the detail view holds it as `let` and is keyed with `.id(selection)` so its `.task` loads each new model. So it owns both columns' models and refreshes the sidebar after the detail's writes: each detail model exposes a counter of saved writes, and the root view reloads the sidebar with `.task(id:)` on it. Pushed screens keep their model in `@State` (each path element gets its own view, so no `.id`) from a factory the root screen's model holds (one per path case and the detail column, nothing else) and the destination mapping passes on. A sheet's factory is held by the model that presents it. How a pushed screen's write refreshes the sidebar beside it in a regular width is undecided: the first such case decides (ask the user). When a sidebar reload finds the selected record gone, the model clears the selection; a pushed screen whose record is gone shows that it no longer exists (not an error).
  - Which sheet (or full-screen cover or popover) is presented is model state: an optional `Identifiable` enum in the presenting model, bound with `.sheet(item:)`; intents set it. The sheet closes itself on its intent's outcome (`if await model.save() { dismiss() }`), which clears it through the binding, and the presenting view reloads its model from `.sheet(item:onDismiss:)`. Confirmation dialogs stay view `@State`; failed-action alerts follow ADR-0011. Sheets are for tasks the user starts and finishes; a sheet's view builds its model from a factory in `@State`, and a multi-step sheet has its own `NavigationStack` with its path in its own model.
  - URLs: the only one handled is the Strava redirect when the Strava app signs in (`ASWebAuthenticationSession` returns its callback to the session); #3 chooses its form and registers it (a URL scheme in `BikeComponents/Info.plist`; a universal link is a capability: ask the user). One `.onOpenURL` on the launch model's root view calls the launch model's `open(_:) async` from a `Task`. While opening, the launch model keeps the latest URL and its stored launch task (not a caller's wait) passes it on when it becomes ready; once ready, `open` passes it on at once; after a failed launch it is dropped. A function in `Presentation/` matches a URL to the app-wide model in `AppModels` that handles it and awaits that model's intent; unknown URLs are ignored. URLs (the redirect carries an authorization code) are never logged or put in an error's detail. No navigation deep links yet.
  - No state restoration (`@SceneStorage`, `NSUserActivity` or stored navigation state): the app reopens at the root with nothing selected.
  - SwiftUI's own navigation only: no `UINavigationController`/`UISplitViewController` wrappers or custom collapse, column or window code. A new navigation or window requirement starts with an experiment against the built app on the simulator (iPhone and a resized iPad window) before custom code is planned.
  - Navigation is tested in the models (selection clears the path and builds the detail model, the root screen's intents change the path, intents present sheets, pushed screens' and sheets' intents report the outcome their views dismiss on, gone records clear the selection, URL matching and keeping). Still no UI tests.
  - With the first screens, check on the simulator that a cold launch from the Strava redirect reaches `.onOpenURL`, that a screen covered by a pushed one reruns its `.task` when it reappears, that selecting another entry in a regular width loads the new detail, that popping back to the sidebar in a compact width keeps selection and path consistent, that clearing the selection in the model returns a compact layout to the sidebar, that replacing a path element gives the pushed screen a new model, that resizing between compact and regular keeps selection and path, and that with multiple scenes off the iPad window still resizes freely and can't open a second window. If one fails, adjust the design, with a new ADR if a rule changes.

- Project file and tools (ADR-0015):
  - `BikeComponents.xcodeproj/project.xcproj` is Xcode 27.2's JSON-style project format. Change it with `xcrun xcodeproj` (`pkg add-local`/`link`, `group add`/`add-file`/`exclude`, `config set`, `setting set`/`unset`/`list`, `target …`), then `xcrun xcprojformatter --update BikeComponents.xcodeproj`. Both ship with Xcode (no ADR-0006 admission). Hand edits only where the tool has no command (e.g. renaming a target), then format and check with `xcodebuild -list` and a build.
  - No committed schemes: `xcodebuild` creates `BikeComponents` and `BikeComponentsKit` automatically, in a fresh clone too. Commit a scheme only when one needs non-default settings (the user makes it in Xcode).
  - Capabilities need an entitlements file and portal setup the tool doesn't cover: ask the user to add them in Xcode, then move any target-level setting into the `.xcconfig` and unset it with the tool.
