# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A bike components inventory app built in Swift and SwiftUI.

## Reference project

Use [investment-simulator-2026](https://github.com/cebartling/investment-simulator-2026) (same author, MIT, checked out next to this repo at `../investment-simulator-2026`) for examples and code reuse. Before writing an ADR or a component, check whether it has already solved the same problem:

- ADRs in `docs/adr/`, e.g. hexagonal architecture, Swift 6 concurrency, `@Observable` presentation models and injection, Swift Testing, CI, release
- Code such as the `HTTPTransport` test seam, the Keychain code behind its `CredentialStoring` port (here a token store inside the Strava adapter, not a Core port: ADR-0003), the `justfile` and the GitHub Actions workflows

Reuse what fits, and record where this project diverges and why. It is a macOS-only, SwiftPM-only app, so its build, bundle, window and distribution choices don't carry over to this iOS app (ADR-0002). Each ADR issue (#7 to #22) lists the relevant prior art.

## Current state

The repository holds `README.md`, `LICENSE` (MIT), an Xcode/Swift `.gitignore` and the docs in `docs/`. There is no Xcode project, Swift package, source code, build tooling or test target yet, so there are no build, lint or test commands. Once a project is added, update this file with them, including how to run a single test.

## Decided

- Platforms: iPhone and iPad, one universal iOS app target. Only the latest OS release is supported, down to the point release, currently iOS/iPadOS 27.2. The minimum always equals the SDK we build with, so never write `#available` checks or fallbacks, not even for point-release APIs. When a new OS release (major or point) ships, the toolchain and minimum move up together. Not macOS, visionOS, watchOS or tvOS. Audience is the author plus TestFlight testers. UIKit only where SwiftUI has no equivalent, wrapped in the UI layer. (ADR-0002)
- Architecture: hexagonal (ports and adapters). Layering rules (ADR-0003):
  - Core (the `BikeComponentsCore` module, ADR-0004) holds the domain model, its rules (wear, service intervals, Strava import reconciliation) and the driven ports. It imports Foundation only: no SwiftUI, UIKit, Observation, SwiftData, Core Data, AuthenticationServices, Security or packages. It does no I/O (e.g. `URLSession`, `FileManager`, `UserDefaults`, `Bundle` resources) and never reads the clock or the current locale, calendar or time zone: pass them in as parameters. There is no clock port. It may create IDs with `UUID()`; any other randomness is passed in. A new import into Core needs a new ADR.
  - Core's domain model types are plain value types (use cases are `Sendable` structs or functions: ADR-0005), never `@Model`, managed objects, SQLite records or Strava JSON types. Adapters map at their boundary; Core has no DTO or mapping layer. Invariants such as unique Strava gear IDs are enforced in Core.
  - Driven ports are protocols owned by Core, named for the role (`BikeRepository`, `RideRepository`, `BikeSource`, `RideSource`). Add a port only when Core needs one. Use cases have no protocols: callers use Core's concrete types.
  - Adapters (persistence, Strava, the SwiftUI UI) depend on Core; Core depends on nothing but Foundation. Each driven adapter is its own module, created when its first code is written. Adapter-internal seams (HTTP transport, Keychain token store) stay inside the adapter; Strava tokens never enter Core. Strava connect, disconnect and connection state go through a Core port (named in #3) that the Strava adapter implements.
  - Views and presentation code use Core's types and ports only, never a driven adapter module. Only the composition root imports adapters.
  - The app target is the composition root. Core gets ports through initializers or parameters, never from singletons, globals or service locators.
  - Core is tested through in-memory fakes of its ports: no UI, disk, network or real clock. No automated import check exists yet, so check Core's imports by hand.
- Project structure (ADR-0004):
  - `BikeComponents.xcodeproj` at the repo root holds one app target, `BikeComponents`, whose sources are a buildable folder, `BikeComponents/`. It holds only `@main` and the composition root: no views, presentation code or domain logic. Code that has to sit beside `@main` (e.g. a `UIApplicationDelegateAdaptor`) is the one exception: keep it minimal and have it forward to Core or `BikeComponentsUI`. The "UI layer" for UIKit wrappers is `BikeComponentsUI`. Change the project in Xcode, never by hand-editing the `.pbxproj` or with a generator. If a change needs the Xcode project or the app's shared scheme (target settings, capabilities, package links, membership exceptions), stop and ask the user to make it in Xcode. Don't edit `.pbxproj` or `.xcscheme` files. App resources (asset catalog, `Info.plist`, entitlements) live in `BikeComponents/`.
  - Every module lives in the local package `BikeComponentsKit/` (`Sources/<Module>/`, `Tests/<Module>Tests/`), iOS only. Its one library product, `BikeComponentsKit`, lists every library target and is the only thing the app links. Add a new module to that product's targets. Modules: `BikeComponentsCore` (Foundation only), `BikeComponentsUI` (views and presentation code; depends on Core only), `BikeComponentsPersistence` and `BikeComponentsStrava` (driven adapters; depend on Core). Only the app target depends on adapter modules. Every module name starts with `BikeComponents`. Adding or splitting a module that fits these rules needs no ADR. A new kind of module, or one that breaks these dependencies, needs a new ADR. Package targets' Swift settings go in `Package.swift`. Create a module with its first code, and give each library module a `<Module>Tests` test target. `BikeComponentsUITests` is the unit test target of `BikeComponentsUI`. Xcode suggests the same name for a UI test target of the app, so an Xcode UI test target must not use Xcode's default name.
  - Access control: `package` for what another package module uses, `public` only for what the app target uses, `internal` (or narrower) otherwise.
  - Third-party packages follow ADR-0006 (below): only the module that needs one (and its tests) uses it, never Core or the app target.
  - Tests run on an iOS Simulator with `xcodebuild test` against the package's generated `BikeComponentsKit` scheme, from `BikeComponentsKit/`, which picks up every `.testTarget` by itself. The app's shared scheme only builds and runs the app. `swift build` and `swift test` on the Mac are not supported: they may build and pass, but they test macOS, which isn't a supported platform, so don't rely on them.
- Concurrency (ADR-0005):
  - Swift 6 language mode in every target. Every target enables the upcoming features `NonisolatedNonsendingByDefault`, `InferIsolatedConformances` and `MemberImportVisibility`: package targets through one shared settings list in `Package.swift`, the app target through its `SWIFT_UPCOMING_FEATURE_*` settings, with the template's `SWIFT_APPROACHABLE_CONCURRENCY` removed (project changes: ask the user). `Package.swift` needs `swift-tools-version` 6.2 or later. Don't enable other upcoming features without a new ADR.
  - Default isolation: Core, Persistence and Strava are nonisolated. `BikeComponentsUI` (`.defaultIsolation(MainActor.self)`) and the app target are `MainActor`. A test target uses its module's isolation. In a main-actor module, mark a type `nonisolated` when it has to leave the main actor.
  - A nonisolated `async` function runs on its caller's actor; actor and main-actor methods run on their own. Use `@concurrent` (only on `async` functions) to move work off the caller deliberately.
  - Core has no actors and no shared mutable state. Domain types are value types that declare `Sendable`. Use cases are structs that declare `Sendable` (it isn't inferred for `public` types), or functions, holding their ports, `async` when they call a port.
  - Driven ports are `Sendable` protocols, `async` for I/O. Adapters hide their isolation behind the port and never block their caller: put blocking or CPU-heavy work in a `@concurrent` function or on the adapter's own actor. Use an actor for adapter state that concurrent calls share, such as the Strava token store and refresh. Actors are reentrant, so the token actor keeps a refresh in progress as a stored task that concurrent callers await, so only one refresh runs at a time. A `Sendable` port can't have an isolated conformance, so a main-actor type implements a port only through `async` methods. The persistence adapter's isolation is set by ADR-0007 (below).
  - In-memory fakes of ports are actors, or final classes that guard their state with Synchronization's `Mutex`. Test targets may import Synchronization (Core's Foundation-only rule covers `BikeComponentsCore`, not its tests).
  - Prefer an actor or a value type. A synchronous adapter class may guard its state with Synchronization's `Mutex`. `@unchecked Sendable`, `nonisolated(unsafe)` and `@preconcurrency` only with a comment saying why the code is safe or which framework forces it.
  - Use structured concurrency (`async let`, task groups). Start unstructured tasks in the UI layer, preferably with `.task`. An adapter may start one only for a task in progress that several callers share or for an `AsyncStream` producer: keep the handle, cancel it when it's no longer needed, and comment why. No `Task.detached`, Dispatch, completion-handler APIs or Combine. Wrap callback-only framework APIs in checked continuations inside the adapter. Use `AsyncSequence`/`AsyncStream` for values over time, and stop the producer when the consumer is cancelled.
  - Long-running work (a Strava import) checks for cancellation between pages, stops promptly, keeps what it already saved, and isn't reported to the user as an error when cancelled. How cancellation is reported to the caller is decided with #18. Back-off waits use a cancellable sleep (`Task.sleep`).
  - No global mutable state: globals and `static`s are `let`s of `Sendable` types.
- Dependencies (ADR-0006):
  - Apple's frameworks first. Never add a package (a `.package` entry, a test-only package, a macro or plugin package, a binary target, or one of Apple's open-source packages outside the SDK) or a tool without an accepted ADR that admits it. You may propose one in an ADR pull request; the user approves by merging.
  - A package's admitting ADR has a "Dependency check" section and must show it clears the bar: MIT, BSD, Apache-2.0, ISC or zlib license (no GPL, LGPL or AGPL), the same for every transitive dependency, built from source (no binary targets), maintained (a release or commit within 12 months, builds with the current Xcode for iOS), usable in Swift 6 mode without concurrency escapes in our code, no data collection unless that is its job, and imported by exactly one named module and its test target (a test-only package: only the test targets its ADR names), never Core, Core's test target or the app target. Its types stay inside that module. Another license, a binary target or a concurrency escape is allowed only if the admitting ADR argues for it. Macros and build plugins also count their build cost against them. See ADR-0006 for the full bar and the fields the dependency check records.
  - Pin each package with `exact:` in `Package.swift`, with a comment `// ADR-NNNN: used only by <Module>.` No ranges, branches or revisions. Commit `BikeComponentsKit/Package.resolved` and the Xcode project's resolved file, and update both when a pin moves. A resolved-file change that moves a transitive dependency is checked against the bar too. CI builds with `-onlyUsePackageVersionsFromResolvedFile`.
  - Updates are manual, one package per pull request, checked when the toolchain moves to a new Xcode or a security fix ships (Dependabot security alerts, not version-update pull requests, are on once the first package arrives). The pull request description repeats the dependency check; don't edit the admitting ADR. An update that no longer clears the bar needs a new ADR. If a package has no version that builds with the new Xcode, or no longer clears the bar, stop the toolchain move and ask the user: a new ADR replaces it, removes it or accepts the exception.
  - Tools are standalone binaries (Homebrew locally), never SwiftPM plugins or packages, even where a plugin version of the tool exists. Formatters and linters are pinned in CI by version and SHA-256; `just` may be unpinned. CI prints every tool's version. When you upgrade a tool locally, move its CI pin in the same change. Actions from GitHub's `actions` org are pinned by major tag; any other action by full commit SHA with its version in a comment.
- Persistence (ADR-0007):
  - One app-wide SwiftData store, `BikeComponents.store` in Application Support. Only `BikeComponentsPersistence` imports SwiftData: not Core, `BikeComponentsUI` or the app target. Its public API opens the store and returns the adapter, through an `async` `@concurrent` function so opening and migrating never run on the main actor. The app's store syncs through CloudKit (ADR-0009, below); test stores pass `cloudKitDatabase: .none`.
  - Fail fast: if the store can't be opened or migrated, throw an error naming the path and the cause, and the app shows it. Never delete, recreate or replace the store with an empty or in-memory one.
  - `@Model` classes are internal to the adapter. Port methods take and return Core value types. Records keep the domain `UUID` as an attribute, and the adapter finds them by it. Mapping a record that can't make a valid Core value throws a descriptive error.
  - The schema follows CloudKit's rules: every attribute optional or defaulted, every relationship optional with an explicit inverse, no `@Attribute(.unique)` or `#Unique`, no `.deny` delete rules. Core enforces uniqueness. Writes upsert by the domain `UUID` (fetch, then update or insert). Saving a bike also fetches by gear ID in the same actor call and throws if a bike with another `UUID` holds it. Only one import runs at a time (how is decided with #3).
  - Threading: one plain actor (not `@ModelActor`, which ran on the main thread when called from the main actor) creates a `ModelContext` from the container in its initializer, keeps both, and implements every repository port. Set `autosaveEnabled` to false explicitly, leave `undoManager` nil, and every write method calls `save()` once before it returns.
  - Migrations: a `VersionedSchema` from `SchemaV1` and a `SchemaMigrationPlan` from the start. Stages are lightweight unless data must be transformed. A version that has reached a TestFlight build is frozen. Each stage has a test that writes an old-version store to a temporary file and reopens it. All other adapter tests use an in-memory configuration, one container per test.
  - The thread checks ran on macOS. The adapter's first tests must check on the iOS Simulator that a port method called from the main actor runs off the main thread, with Core Data's concurrency assertions on (`com.apple.CoreData.ConcurrencyDebug` = 1; how it reaches the generated test scheme is worked out with #16). If either check fails, stop and revisit ADR-0007.
- State management (ADR-0008). Every feature follows this pattern:
  - Domain rules live in Core. Screen logic lives in an `@Observable` presentation model in `BikeComponentsUI`: screen state, intent methods (`load()`, `save()`, …) that call Core's use cases and ports, and mapping of results and errors to display state (errors: #18). Derived values are computed properties.
  - A model is an `@Observable final class` named `<Screen>Model`, main-actor through the module default, never `nonisolated`, and declares no `Sendable` conformance (main-actor isolation makes it implicitly `Sendable`). No `ObservableObject`, `@Published`, `@StateObject`, `@ObservedObject` or `@EnvironmentObject`.
  - Each model is in its own file, `<Screen>Model.swift`, in `Sources/BikeComponentsUI/Presentation/` (grouped by feature inside it). Every file there (models, their extensions, the display-state types they expose) imports Foundation, Observation and `BikeComponentsCore` only, never SwiftUI or UIKit. Views live outside that folder. The compiler only stops a model naming SwiftUI's declarations: review checks that models don't reach view-side declarations (typealiases, inferred SwiftUI types, views).
  - A model's initializer stores its dependencies and sets initial state only: no port calls, no tasks. Loading is an `async` method the view calls from `.task`.
  - Intent methods that call Core are `async`. Views call them from `.task`, `.task(id:)`, `.refreshable` or a `Task` in a button action. A model starts no unstructured task, except an app-wide model running work that must outlive a screen (the Strava import), which keeps the handle, can cancel it and comments why. A button `Task` isn't cancelled with the view, so intents report their outcome in state or a return value and the view only acts on it (`if await model.save() { dismiss() }`).
  - Views are thin: they read model state, bind with `@Bindable`, call intent methods, and never call a use case or port. View `@State` holds only ephemeral state no rule depends on (focus, scroll position, confirmation dialog shown, section expanded). Selection, navigation state and which sheet or destination is presented: #17. A view with only ephemeral state needs no model. A model may own the models of the parts it presents.
  - Models expose values, not formatted text. Views format with `FormatStyle` through `Text(_:format:)` and similar APIs, which apply the environment's locale; a view calling `formatted(_:)` itself passes the environment's locale. A model that needs the current date, a calendar or a time zone gets it passed in (how: ADR-0010, below). APIs only a view can reach (e.g. the `webAuthenticationSession` environment value) are called by the view, which hands the result to the model (what is handed over: #3).
  - The store is the source of truth. Models hold copies loaded through Core, load when their screen appears and reload (or update from the use case's result) after their own writes. When a write changes another screen on display, the model that owns both refreshes the other (a view that owns both only chains the two intent calls). No app-wide cache of domain data, and no change-notification port yet (revisit if refreshing by hand gets awkward). Writes from other devices come through ADR-0009's remote-change port (below).
  - App-wide state (Strava connection state, import progress) lives in app-wide models built once by the composition root and kept in `@State` on the `App`. Ones that need a repository are built after the store opens (ADR-0007: async, can fail); until then the `App` holds the launch model (ADR-0010, below), which keeps them once they are built. The import runs there, so it outlives the screen that started it and can be cancelled. Cancellation isn't shown as an error. A screen showing imported data is given the import model and reloads when it reports saved progress (e.g. `.task(id:)` on a counter it exposes; what it reports: #3).
  - Every model has one owner: the `App`, or the view (`@State`) or model that presents the screen. A view given a model holds it as `let` or `@Bindable var`, never `@State`. A view that keeps a model built from an input (e.g. a bike ID) in `@State` gets `.id(input)` so the model is rebuilt when the input changes, or its parent model owns the model and passes it in. Models reach views through view initializers, never `@Environment`. Owners build models through factory closures, and nothing besides the system frameworks' own values goes in the environment (ADR-0010, below).
  - Model tests in `BikeComponentsUITests` build models with Core's real use cases over in-memory fakes of the ports, call intent methods and check state. Views have no unit tests.
- Sync and backup (ADR-0009):
  - SwiftData's CloudKit mirroring syncs the whole store (bikes, rides, components, installations, service records) to the user's private CloudKit database. The app's `ModelConfiguration` passes `cloudKitDatabase: .private(<container identifier>)`, never `.automatic`. Adapter tests keep `.none`. No export or import file yet. Per-device state (an import's resume point, last sync time) never goes in the synced store; where it lives is decided with #3.
  - The iCloud (CloudKit, with the container) and Background Modes (Remote notifications) capabilities are Xcode project changes: ask the user. Only `BikeComponentsPersistence` knows about CloudKit; it may import Core Data for the debug-only schema initialization.
  - The store works without iCloud: a signed-out user is not an error. Forum reports (unverified) say signing out later removes the local copy and can lose changes not yet uploaded. ADR-0007's fail-fast rule still applies when the store can't be opened or migrated.
  - Duplicates from other devices are expected. Core reconciles bikes sharing a Strava gear ID and rides sharing a Strava activity ID: keep the smallest `UUID`, move everything app-owned (installed components, installations, service records and any other app-owned data) to it, delete the rest, all in one port call and one save. Reconcile bikes before rides; rides on a losing bike move to the winner, and a ride whose bike is missing is linked by its stored Strava gear ID. A bike save that fails ADR-0007's gear ID check because a duplicate arrived is expected: Core reconciles and retries once; a second failure is a real error. Reconcile at launch, when the app becomes active, at the start of every import (before its upserts), and when the remote-change port reports changes from another device. Scan the whole store; no history token. Reconciliation runs under the imports' one-at-a-time guard: never during an import's page, and the import reloads its bikes after one. Combine triggers that arrive while one is running or waiting.
  - Remote changes: one narrow Core port (an `AsyncSequence`, implemented by the persistence adapter) reports only that changes from another device arrived, not which records. An app-wide model on the `App` consumes it from the root view's `.task`, runs reconciliation for each report, then increments a counter; screens showing synced data take that model and reload with `.task(id:)` on it. Repositories still don't publish changes (ADR-0008), and this device's own writes refresh screens as ADR-0008 says.
  - Conflicts are the framework's (reported as last writer wins; Apple doesn't document it); add no conflict handling. Deletes propagate to every device and are permanent.
  - Once a schema version is deployed to CloudKit production, later versions only add models and attributes: never delete, rename or change the type of existing ones. Devices may run different app versions, so a new attribute's default must map to a valid Core value. Records can arrive before their parents: reads skip a record whose required relationship hasn't arrived (it's incomplete, not invalid; any other unmappable record still throws), and reconciliation never matches on a missing Strava ID. Initialize the development schema by hand from a debug build when the schema changes (a debug-only public function in `BikeComponentsPersistence`, called by the app only when a launch argument asks); deploy to production in the CloudKit Console before a TestFlight build with a new schema version.
  - Strava tokens never sync: each device that imports connects to Strava itself, with non-synchronizable Keychain items.
  - The cross-context checks ran on macOS without CloudKit. Before the first TestFlight build with sync, check on two devices that imported changes are seen and reconciled, that a signed-out device works, what signing out and back in does to changes not yet uploaded, and that the store opens when iCloud is unavailable or full. If not, stop and revisit ADR-0009.
- Dependency injection (ADR-0010):
  - Initializer injection everywhere: Core, adapters, models, views. No property injection, container, service locator, DI library or dependency in the environment. No default arguments for dependencies (ports, factories, clock, calendar): every caller, tests included, passes them.
  - Models take the Core ports they use (`any BikeRepository`, …) and build the use cases they call from them. Views get a model, or a factory closure for the model they keep in `@State`, never a port, adapter or use case.
  - Child models come from factory closures that take only what varies (`makeDetailModel: (Bike.ID) -> BikeDetailModel`), written by the composition root. Use a factory even when the parent could build the child itself. A parent's test passes a closure building the child over the same fakes.
  - The composition root is the `@main` `App` plus plain wiring functions (one per model) in `BikeComponents/`. Only it names adapter types, opens the store, builds the Strava adapter, and passes `{ Date.now }` and `Calendar.autoupdatingCurrent`. Everything the wiring names is `public` (ADR-0004): model initializers, `LaunchModel`, `AppModels` with an explicit `public init`, the root view, adapters' open functions and initializers, and the ports and Core types in those signatures. Use cases stay `package`. Each adapter is built once. It holds no logic and has no unit tests: anything with a decision goes in a model.
  - Launch: `App.init` opens nothing and keeps only `LaunchModel` (in `BikeComponentsUI`) in `@State`. It takes `start: () async throws -> AppModels` from the composition root, which opens the store, builds the adapters and returns `AppModels` (the app-wide models and a factory for the root screen's model, which the view showing the app builds and owns; how many scenes: #17). State: opening, ready(`AppModels`) or failed(error). The root view calls `launch()` from `.task`. The first call starts `start` in a task the model stores (ADR-0008's app-wide exception, with a comment) and every call awaits that task, so the store opens once and a view going away never cancels the launch. Every app-wide model is built by `start`, and kept on the `App` through the ready state. A failed launch shows the error until relaunch: no retry, no fallback store. Wording: #18.
  - The current date is `now: () -> Date`, called each time an intent needs it; a calendar or time zone is a `Calendar` (use its `timeZone`). Tests and previews pass fixed values. Core and `Presentation/` files never use `Date.now`, `Date()`, `Calendar.current`, `TimeZone.current` or `Locale.current`.
  - Fakes go in through the shipping initializers: no test-only or preview-only initializers, no "am I in a test or preview" checks in shipping code. One in-memory fake per port, written when a test first needs it and shared by the test targets that need it (where: #16). Previews, if #16/#19 adopt them, use the same fakes and fixed date and calendar, never the real store, Strava or Keychain.
  - No singletons of our own anywhere (`static let shared`, globals or statics holding a dependency, type-based resolvers). `Sendable` `let` constants are fine. System shared instances (`URLSession.shared`, `FileManager.default`, `UserDefaults.standard`, `NotificationCenter.default`, `UIApplication.shared`) only in adapters and the composition root; an adapter takes one through its initializer when its tests need to replace it. Views use environment actions (`openURL`) instead.
  - No custom `EnvironmentValues` entries yet. One for a view-only concern no model reads needs no ADR; one carrying a dependency does.

## Open decisions

Much of the architecture is still undecided. Don't assume any of the following until an ADR records it:

- testing framework (Swift Testing or XCTest)

Architecture Decision Records live in `docs/adr/` (see ADR-0001 for the conventions). ADR files are named `NNNN-kebab-case-title.md`, start from `docs/adr/template.md`, use the Nygard format, and are listed in `docs/adr/README.md`. Record each of these decisions as an ADR when it is made, then update this file and the requirements in `README.md` to match.
